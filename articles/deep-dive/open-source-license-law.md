# 开源协议不是君子协议

「开源协议就是个君子协议」——这句话在技术群里出现的频率很高，通常出现在两种场景：有人担心用了 GPL 代码会被起诉，或者有人觉得自己的项目挂了 MIT 却没人遵守也无所谓。

这两种感受都对了一半，但结论都错了。开源许可证在法律上**不是道德宣言，而是一份附条件的著作权许可合同**：你获得了复制、修改、分发的权利，代价是遵守它列出的条件；条件不满足，许可自动失效，你的使用就从「被授权」变成「无授权复制」——也就是侵权。

这一篇不讨论「哪个协议更好」，只梳理三件事：它们各自约定了什么、在法律上能主张到什么程度、工程上怎么把它落成可执行的规范。

> [!NOTE]
> 本文是技术向的条款梳理，不构成法律意见。涉及具体商业决策请交由律师判断。

## 一、法律定性：为什么它不只是「君子协议」

理解开源协议，先要分清三个层次：

| 层次 | 是什么 | 违反后果 |
| --- | --- | --- |
| 著作权 | 代码自动产生的专有权利，许可证不转移所有权 | 未经许可复制/分发 → 著作权侵权 |
| 许可条件 | 许可证列出的义务（署名、开源、专利授权等） | 条件不满足 → 许可终止，回到侵权状态 |
| 合同关系 | 部分法域将许可证视为双方合意 | 违约之诉，可与侵权竞合 |

关键点在于：**开源不是放弃版权**。作者放弃的是「排他使用的部分权能」，保留的是「依条件授权的权利」。所以违反 GPL 的后果不是「被社区骂」，而是可能被要求停止分发、公开衍生代码、赔偿损失。

至于「君子协议」的印象从哪来——来自**执行率**而非**效力**。绝大多数权利人不会为一次违规去起诉，原因很实际：诉讼成本远高于损失、举证需要做代码同一性鉴定、被告往往是小团队。但这属于「没人告」，不等于「告不赢」。

## 二、四类谱系

先把常见协议按「传染范围」排开，这是工程上最有用的一根轴：

| 类型 | 代表 | 传染范围 | 典型使用 |
| --- | --- | --- | --- |
| 宽松型 | MIT、BSD-2/3、Apache-2.0 | 几乎无，保留声明即可 | 库、SDK、基础设施 |
| 弱传染（文件级） | MPL-2.0、EPL-2.0 | 修改过的文件需开源 | 可被闭源产品集成的中间件 |
| 弱传染（链接级） | LGPL-2.1/3.0 | 修改库本身需开源，调用方可闭源 | 系统库、运行时 |
| 强传染 | GPL-2.0/3.0、AGPL-3.0 | 衍生作品整体需以同协议开源 | 应用、工具链 |
| 非开源（源码可见） | SSPL、BUSL、Elastic License | 由自定义条款决定 | 商业产品限流策略 |

最后一类需要单独说清：**SSPL、BUSL 这些不是开源许可证**，它们不符合 OSI 的开源定义（尤其歧视性使用限制），正确叫法是 source-available。把它们当开源用，是合规事故的常见起点。

## 三、逐个拆条款

### MIT / BSD：短，但缺一块

MIT 全文只有一段：保留版权声明与许可声明、提供免责声明。它**没有明示专利授权**。

这在实际中是真实风险：某公司贡献了带专利的代码到 MIT 项目，专利持有人后来主张专利，MIT 文本里找不到任何对抗依据（除非适用「默示许可」理论，而该理论在各国适用标准不一）。BSD-3-Clause 在 MIT 基础上多了一条：不得用作者名义为衍生产品背书。

> [!TIP]
> 涉及专利敏感领域（编解码、通信、图形算法）的库，如果上游是纯 MIT/BSD，企业合规上通常要求单独做专利尽调，而不是看许可证就放行。

### Apache-2.0：宽松型里最完备的一份

它在 MIT 的基础上补了四块：

1. **明示专利授权**（第 3 条）：贡献者授予你使用其专利的权利，范围是该作品的贡献。
2. **专利反击条款**：如果你就该项目提起专利诉讼，你对它的专利授权立即终止——这是防止「拿开源代码然后起诉原作者」的机制。
3. **修改标注义务**：修改过的文件需显著说明你改过。
4. **NOTICE 传递**：如果项目带 NOTICE 文件，分发时需一并保留其内容。

它不授权商标。这一点常被忽略：用 Apache 项目的名字做产品名，不在这份许可范围内。

### GPL 家族：传染的定义与边界

GPL 的核心不是「用了就要开源」，而是分两步：

- **触发点**：只有「分发」（distribution / convey）才触发义务。自己内部改、内部部署，通常不触发（AGPL 例外，见下）。
- **义务范围**：分发二进制时，须向接收者提供**对应源码**（Corresponding Source），且衍生作品整体仍以 GPL 授权。

真正的难点在于「衍生作品」的边界。GPL 文本用的是「基于该程序的作品」这一表述，判例与社区共识大致收敛为：进程间通过标准接口通信通常不构成衍生（如 fork/exec 调 CLI 工具）；静态链接、把代码复制进同一编译单元通常构成；动态链接处于灰色地带——FSF 认为构成，部分企业法务认为不构成。

GPLv3 相比 v2 增加了几个关键变化：

| 条款 | 内容 | 实践意义 |
| --- | --- | --- |
| 明示专利授权 | 与 Apache-2.0 类似 | 减少专利伏击 |
| 反 Tivoization | 需提供「安装信息」 | 硬件锁固件的场景不能只给源码不给刷机途径 |
| 终止与恢复 | 首次违规并在 30 天内纠正可自动恢复授权 | 给了纠错窗口，降低了「一次失误永久失权」 |
| 与 Apache-2.0 兼容 | v2 不兼容，v3 兼容 | 混用前必须确认版本 |

版本差异是合规事故的高发区：**「GPL-2.0-only」和「GPL-2.0-or-later」是两个不同授权**，前者不能升到 v3，也因此不能与 Apache-2.0 代码合并。

### AGPL：把「网络服务」也算进来

AGPL 相对 GPL 只多一条（第 13 条）：**通过网络交互使用该程序，视为分发**。这一条把 SaaS 场景纳入义务范围——你改了个 AGPL 数据库并对外提供 API，用户有权要求拿到你改后的源码。

这是「我要做闭源 SaaS，能不能用这个库」这个问题最常见的翻车点。

### MPL-2.0：文件级，可组合

MPL 的传染以**文件**为单位：你修改过的那几个文件需以 MPL 公开，项目其余部分可以闭源。它同时允许把 MPL 代码与 GPL 代码组合（通过 secondary license 条款），在「想开源改动但不想开源产品」的诉求下，比 GPL 更实用。

### CC 家族：协议本身没错，错在用错地方

CC（Creative Commons）是**内容**许可，四个模块的组合：

| 模块 | 含义 |
| --- | --- |
| BY | 署名 |
| SA | 相同方式共享（传染） |
| NC | 禁止商业使用 |
| ND | 禁止演绎 |

加上 CC0（放弃权利，进入公有领域，但在部分法域人格权不可放弃）。

问题在于：**Creative Commons 官方明确不建议把 CC 协议用于软件**。原因很直接——CC 系列没有处理源码分发、专利授权、链接与衍生作品定义这些软件特有的问题。把 CC BY-NC 挂在一个代码库上，会产生一堆无法回答的问题：什么叫商业使用？内部使用算不算？公司内部部署算不算？

另外，NC 与 ND 条款本身与开源定义冲突（不得歧视使用领域、不得限制修改），所以 CC BY-NC 的代码**既不是开源，也不能与 GPL 代码合并**。CC 的正确用途是文档、图片、数据集、教材。

## 四、法律效力：判例层面的现实

公开可查的司法实践中，开源许可证的可执行性已经被多国法院确认：

- **美国**：Jacobsen v. Katzer（联邦巡回上诉法院，2008）认定开源许可证中的条件是版权许可的**条件**而非单纯契约条款，违反即构成版权侵权，权利人可申请禁令。这一判决确立了「开源协议不只是合同，还能走侵权路径」的基础。
- **德国**：Welte v. D-Link（法兰克福地方法院，2006）确认 GPL 在德国法下的效力，并支持了停止侵权与费用承担。
- **中国**：公开报道的国内判决中，已有法院在处理涉 GNU/Linux 系统软件的著作权纠纷时，认定 GPL 系列协议对使用者具有约束力（如数字天堂与柚子科技案，法院讨论了 GPL v3 的合同性质）。具体裁判观点以公开文书为准。

据此可以说清楚一句话：**开源协议是被司法实践承认的可执行许可，效力真实存在。**

但同时要承认另一面：**执行是选择性的**。绝大多数违规从未进入诉讼，原因包括：

1. 权利人缺乏诉讼资源或意愿（个人开发者、基金会）；
2. 举证成本高：需证明代码同一性、需证明分发行为发生；
3. 赔偿额常低于诉讼成本，商业上不划算；
4. 社区更倾向于先私下联系、公开发声、要求整改。

所以真实世界的执法结构是：**法律效力兜底，声誉压力在前**。这正是「君子协议」这个说法的现实来源——不是没有法，而是大多数人先用成本更低的方式解决。

## 五、工程规范：把协议变成可检查的流程

协议条款再清楚，落不到流程上就只是 README 里的一行字。可落地的做法有这几层：

**1. 每个文件标清楚**

用 SPDX 标识符，机器可读、无歧义：

```text
// SPDX-License-Identifier: Apache-2.0
// Copyright 2026 Example Org
```

`GPL-3.0-or-later`、`Apache-2.0`、`MPL-2.0` 这些写法来自 [SPDX License List](https://spdx.org/licenses/)，不要在文件里手写「GPL」——那等于没写，因为无法区分版本与 only/or-later。

**2. 进出双向检查**

合规不是只看「我引用了谁」，还要看「我被谁引用」：

| 方向 | 检查内容 |
| --- | --- |
| Inbound | 引入的依赖是什么协议，是否与本项目协议兼容 |
| Outbound | 本项目以什么协议分发，是否被依赖方的义务反向约束 |

**3. CI 里加一道门**

- `license-checker` / `licensee`（Ruby）/ `pip-licenses`：扫依赖树协议清单
- `ScanCode` / `FOSSA`：做代码片段级匹配，能发现「复制粘贴进来但没有声明」的情况
- `REUSE`：校验每个文件是否带 SPDX 头
- SBOM（SPDX 或 CycloneDX 格式）：把许可证信息随产物一起交付，供应链下游能直接读取

**4. 兼容性矩阵要背下来**

最常见的三个坑：

- Apache-2.0 代码 **不能**并入 GPL-2.0-only 项目（附加限制冲突）；可以并入 GPL-3.0
- GPL-2.0-only 代码 **不能**升级到 v3 使用
- AGPL 代码在 SaaS 场景即触发源码提供义务

## 六、结论

回到最初那个问题：开源协议是不是君子协议？

**法律上不是。**它是可执行的附条件许可，判例已经确认违反可构成侵权或违约，能主张停止侵害、开源衍生代码乃至赔偿。

**实践中有「君子」成分。**执行依赖权利人主张，成本高、发生率低，所以大量违规在现场不会被追。这构成了一种「低成本违约、低成本维权」的均衡，也让很多人误以为它没有牙齿。

对开发者更实用的结论是这三句：

1. 用别人的代码前，先看清 SPDX 标识与版本号，别停在「MIT / GPL」这种模糊认知上。
2. 自己发项目时，协议选型要和商业模式对齐——要防止被白嫖选 copyleft，要被广泛集成选 permissive，要开源但保商业空间看 MPL。
3. 协议写进 CI，而不是写进 README 就算完；能被自动检查的条款才真正生效。
